# PRD — `prd-sync`

> Idempotent synchronization of a PRD in Markdown to GitHub Issues + GitHub Projects v2.

| Field             | Value                                     |
| ----------------- | ----------------------------------------- |
| Version           | 1.0                                       |

| Stack             | Node 24 · TypeScript · pnpm               |

---

## 1. Context and problem

Teams that work with AI author their PRDs in Markdown, versioned in the repo alongside code. However, the backlog lives in an external tool (Jira), which forces manual copying of every user story and task into the board. The result is the usual one: the PRD and the board diverge within three days, and nobody knows which one is authoritative.

GitHub Projects v2 already has everything necessary to replace a Jira board — issue hierarchy, custom fields, iterations, board views and roadmap — but it offers no way to populate it from a document.

`prd-sync` fills that gap: the PRD in the repository is the single source of truth, and the GitHub board is a projection generated automatically on every push.

## 2. Goals

| #   | Goal                                              | Success metric                                               |
| --- | ------------------------------------------------- | ------------------------------------------------------------ |
| O1  | Eliminate manual transcription of the backlog     | 0 issues created by hand from a PRD                          |
| O2  | Keep PRD and board consistent                     | Re-running the sync on an unchanged PRD produces 0 mutations |
| O3  | Make backlog changes reviewable                   | Every backlog change goes through a PR with a visible plan   |
| O4  | Replace Jira for personal and small-team projects | A complete project managed end-to-end without Jira           |

## 3. Out-of-scope

- **Bidirectional sync.** Changes made in the GitHub UI are not written back to the Markdown. The PRD is authoritative, always.
- **Migration from Jira.** Out of scope for v1.
- **Visual PRD editor.** The PRD is written by hand or generated by an LLM.
- **Support for GitHub Enterprise Server.** Only `github.com` in v1.
- **Lifecycle automation of issues** (close, move columns). The sync creates and updates content; the team manages state on the board.

## 5. Input contract — PRD format

The parser accepts one or multiple Markdown files. The recognized structure is:

```markdown
# <PRD Title>

## E1 — <Epic name>

<Free description of the epic.>

### US-01: As a <role>, I want <action> to <benefit>

**Priority:** P0
**Estimate:** 3

#### Acceptance criteria

- Given a valid PRD, when the sync runs, then one issue per story is created.

#### Tasks

- [ ] Define the `UserStory` type
- [ ] Implement the parser with `remark`
- [ ] Unit tests for the parser
```

Contract rules:

- `## E<n> — <name>` defines an **epic**.
- `### US-<n>: <title>` defines a **user story**. The ID `US-<n>` is the synchronization key and **must not be reused or reordered**.
- `#### Tasks` contains a list of checkboxes; each is a **task**.
- `#### Acceptance criteria` and the free text under the story form the issue body.
- Bold fields (`**Priority:**`, `**Estimate:**`) are optional and map to Project fields.
- Any unrecognized section is ignored without error.

> This document itself complies with the contract: section 8 is the actual backlog for the project and serves as a test fixture.

## 6. Domain model

```ts
type Priority = 'P0' | 'P1' | 'P2' | 'P3';

interface Task {
  key: string; // "US-01.T2" — derived from the index
  title: string;
  done: boolean;
}

interface UserStory {
  key: string; // "US-01"
  title: string;
  epicKey: string | null;
  body: string; // description + acceptance criteria in Markdown
  priority?: Priority;
  estimate?: number;
  tasks: Task[];
}

interface Epic {
  key: string; // "E1"
  title: string;
  body: string;
}

interface Prd {
  title: string;
  sourcePath: string;
  epics: Epic[];
  stories: UserStory[];
}
```

## 7. Technical requirements

### 7.1 Stack

| Area             | Choice                               | Rationale                                                       |
| ---------------- | ------------------------------------ | --------------------------------------------------------------- |
| Runtime          | Node 24 LTS                          | Native `fetch`, no polyfills, native TS type stripping           |
| Language         | TypeScript (strict)                  | Explicit contracts between parser, planner and client           |
| Package manager  | pnpm                                 | Author's preference                                             |
| Markdown parsing | `unified` + `remark-parse` (mdast)   | Regex over Markdown is brittle; AST tolerates format variations |
| GitHub client    | `@octokit/rest` + `@octokit/graphql` | Projects v2 is GraphQL-only                                     |
| Validation       | `zod`                                | Config and API responses validated at runtime                   |
| CLI              | `commander`                          | Sufficient without heavy dependencies                           |
| Tests            | `vitest`                             | Author's standard                                               |
| Bundling         | `tsdown` → ESM + bin                 | Executable via `npx` in Actions                                 |

### 7.2 Mapping to GitHub

| PRD concept         | GitHub artifact                                             | API                                         |
| ------------------- | ----------------------------------------------------------- | ------------------------------------------- |
| Epic                | Issue with label `epic:E1` (or _issue type_ `Epic` in orgs) | REST `POST /repos/{o}/{r}/issues`           |
| User story          | Issue, sub-issue of the epic                                | REST + `addSubIssue`                        |
| Task                | Sub-issue of the user story                                 | `POST /repos/{o}/{r}/issues/{n}/sub_issues` |
| Board               | Item in Project v2                                          | GraphQL `addProjectV2ItemById`              |
| Priority / Estimate | Project fields (single-select / number)                     | GraphQL `updateProjectV2ItemFieldValue`     |

Critical implementation notes:

1. The REST endpoint for sub-issues expects `sub_issue_id` — the **internal id** of the issue, not its number. You must persist each created issue's `id`.
2. GraphQL alternative: `addSubIssue(input: { issueId, subIssueId })`. If the API returns a feature error, retry with header `GraphQL-Features: sub_issues`.
3. `gh` has no native command for sub-issues; it is not a fallback option.

### 7.3 Idempotency

Each created issue carries an invisible HTML marker at the end of the body:

```html
<!-- prd-sync:key=US-01 source=docs/prd/checkout.md -->
```

The sync engine:

1. Reads all issues in the repo with the label `prd-sync` (a single paginated query).
2. Extracts the `key` from each marker and builds an index `key → issue`.
3. Compares against the parsed PRD and produces a **plan**: `create` / `update` / `orphan`.
4. `update` emits a mutation only if the content hash changed.
5. `orphan` issues (those whose story disappeared from the PRD) are **not deleted**: they are labeled `prd-sync:orphan` and reported.

Hard requirement: running the sync twice in a row on the same PRD must produce zero mutations on the second run.

### 7.4 Authentication and permissions

- The default `GITHUB_TOKEN` from Actions **does not have write access to Projects v2**. A classic PAT with `project` (and `repo`) scope or a GitHub App with `Projects: write` org permission is required, stored as secret `PRD_SYNC_TOKEN`.
- The token must never be logged. Validate its presence and scopes at startup with an actionable error message.

### 7.5 Rate limits

Bulk issue creation collides with secondary rate limits. Requirements:

- Serialize writes (no concurrency) with a configurable pause between mutations (default 500 ms).
- Exponential backoff on `403` with `retry-after` support.
- A PRD with 100 tasks must complete without aborting.

### 7.6 Configuration

File `prd-sync.config.json` at the repository root, validated with `zod`:

```json
{
  "repo": "luchosr/nomadhome",
  "projectNumber": 3,
  "sources": ["docs/prd/**/*.md"],
  "syncLabel": "prd-sync",
  "fieldMapping": {
    "priority": "Priority",
    "estimate": "Estimate"
  },
  "throttleMs": 500
}
```

## 9. Risks

| Risk                                                    | Impact | Mitigation                                                                                  |
| ------------------------------------------------------- | ------ | ------------------------------------------------------------------------------------------- |
| Sub-issues API contract changes                         | High   | Isolate in the client; REST ↔ GraphQL fallback; contract test in CI                         |
| Secondary rate limits for large PRDs                    | Medium | Serialized throttle and backoff (US-05)                                                     |
| Reordering or renumbering IDs in the PRD breaks mapping | High   | Document that IDs are immutable; detect massive orphaning and abort requesting confirmation |
| Issue duplication due to idempotency bug                | High   | Mandatory dry-run in PR; double-run test in CI                                              |
| PAT with `project` scope is a broad credential          | Medium | Document alternative with GitHub App and minimal permissions                                |
